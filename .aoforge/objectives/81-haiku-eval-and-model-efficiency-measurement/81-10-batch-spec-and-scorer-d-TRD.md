# TRD 81-10: Batch spec and scorer for D (UI judge)

<objective>
Make test D runnable and scorable: one headless session per surface, model and repeat that judges every state of
that surface with the engine's own per-state rubric and returns engine-shaped results, and a scorer that aggregates
the three repeats per state exactly as the engine aggregates its live samples.

Purpose: SC-1/SC-3 for test D (per-state accuracy and escalation frequency). This is the agent route the user
chose: the engine's `--judge live` path needs an API key, so the same judgment is made through a subscription-auth
Claude Code session instead, keeping the engine's text, schema and vote rules.
Output: batch module, scorer, canned judge outputs, tests. No live call.
</objective>

<codebase_examples>
Engine exports (`plugins/aoforge-stack-flutter/lib/flutter-ui-eval.cjs`, this checkout): `buildVisionRequest(request)`
returns `{model, body}` whose `body.messages[0].content[1].text` is the per-state judge text:
"You are a strict UI-defect detector. Evaluate this screenshot for state "<state_id>".\nExpected appearance:
<expected>\nScore DEVIATION from expected, not open-ended aesthetics. Taxonomy — defect types: ...; severities:
....\nIf it matches expected with no defects, return is_broken:false, defects:[]." It reads the screenshot (base64)
and calls `judgeModel(judgeProfile())`; `judgeProfile` honours `AOFORGE_MODEL_PROFILE`, so set it to `balanced` in
the call's process env (or temporarily) to keep it off any project config. `visionPerceptualSchema()` returns the
per-state schema `{is_broken, matches_expected, confidence, defects[{type, severity, region, rationale}]}`.
`aggregateVotes(samples)` → `{is_broken, votes, split, tie}`; `scoreState({samples})` → `{verdict:
'pass'|'fail'|'review', advisories, votes}` (HIGH-severity-only fail); `judgeEscalation` treats split reviews of
expect-pass states as the escalation trigger.

Fixtures from TRD 81-05: `scripts/eval81/fixtures/D/states.json` (`surfaces[{surface, expected per viewport}]`,
`states[{id, surface, viewport, png}]`), `labels.json` (answer key), `png/<id>.png`.
</codebase_examples>

<gotchas>
- Keep the user's numbers: 24 runs, one session per surface (about five states each), not one per state. The
  engine judges each state in its own call; in one session the judge can compare states. Mitigations, all stated in
  the report: per-repeat shuffled order (seed = repeat x 1000 + surface index), every state judged against the same
  surface-level expected text, and an instruction to judge each screenshot on its own against the expected text.
- Copy each PNG into the work dir under its neutral id; the prompt names the absolute work-dir path (the session's
  Read tool needs a path it can open).
- Schema for the run: `{type: object, required: [results], properties: {results: {type: array, items: {type:
  object, additionalProperties: false, required: [state_id, is_broken, matches_expected, confidence, defects],
  properties: {state_id: {type: string}, ...visionPerceptualSchema().properties}}}}}`.
- Cap: `capFor({role: 'judge', model, batch: 'D'})`; timeout 10 minutes; models haiku and sonnet; order interleaved
  as in A.
- The ui-evaluator role's tier (flutter pack `aoforge-stack.json` `models.ui-evaluator`) is the tier the vision
  calls use; that is the decision this batch informs (MEF-06 starting tier).
</gotchas>

## Test list

Outermost first.
batch D
1. `runs()` returns 24 valid descriptors: kind `prompt`, agent null, plugin null, tools `['Read']`, a jsonSchema of
   the shape above, ids `D-<surface>-<model>-r<n>`, caps with bases.
2. A run's prompt contains, for each state of its surface, exactly the engine text `buildVisionRequest` returns for
   that state (computed in the test) and the work-dir screenshot path; the state order differs between r1 and r2 and
   is identical across two calls of runs().
3. No prompt or materialised file name contains a label word or a labels.json field; `batches/D.cjs` does not
   reference labels.json.
4. materialize copies only that surface's PNGs, renamed `<id>.png`; collect returns `{results}` from
   structured_output, or from a fenced json block, or `{results: [], parse_error}`.
score D
5. Three samples broken/broken/ok on a broken-labelled state -> majority broken, correct, split true.
6. ok/ok/ok on an ok state -> correct, no split; ok/broken/ok on an ok state -> correct, split, counted as an
   engine-rule escalation.
7. broken majority on an ok state -> wrong (a false fail); ok majority on a broken state -> broken_missed.
8. A state with one missing sample is aggregated on two and flagged; with none it is unjudged and excluded.
9. score() over a hand-built root of 6 runs (one surface, both models, 3 repeats) writes the 81-02 batch result
   object for role `ui-evaluator` with accuracy, broken_missed, split_rate, engine_escalations, per-sample accuracy,
   and the defect-type and severity breakdowns.
